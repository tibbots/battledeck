# Image assets

Every bitmap under `UI/Images/` is generated by a script in `tools/`. Nothing there was drawn by
hand, and nothing there should be edited by hand. Two of the sets are cut from real Blizzard
material (the rank medal sheet, the hero portraits); three are drawn from scratch against
measured geometry (the "no rank" disc, the penalty triangle, the free-rotation mark).

## The rule

To change an image, change the generating script and re-run it. Never open a PNG in an editor
and touch pixels directly — every generator below carries its own measurements against a
reference, and a hand edit throws those away silently, until the next regeneration overwrites the
hand edit anyway. Each asset below is named together with the script that owns it.

## Rank medals (`build-rank-assets.py`)

There is no official source with ready-made medals per division — every template shows the tiers
with a burnt-in "1". The 27 PNGs (160×176, RGBA, about 1.4 MB total) are therefore derived, not
copied, and generated by `tools/build-rank-assets.py`:

- the digit is removed by diffusion inpainting
- the division is re-set in **Segoe UI Black** (not Blizzard's own typeface)
- Master and Grand Master are cut out of a screenshot instead, since the source sheet carries no
  digit to remove for those two tiers
- source URLs are recorded in the script header

Image paths are resolved only through `HotsRankImages.PathFor()` — never assembled a second time
at another call site. That exact duplication already happened once, with the battletag-to-Windows-user
derivation this app no longer has.

### The source sheet axis trap

The five medals on the source sheet do **not** sit on a 160 px grid. Their axes of symmetry sit
at:

```
x = 80.5 / 236.5 / 389.6 / 547.6 / 710.5
```

Cutting at plain 160-point boundaries puts a medal up to **12 px** too far left, and with it the
division digit visibly too far right — correct for Bronze by chance, increasingly wrong after
that. The script measures the axis per medal from the mirrored alpha silhouette and cuts centred
on it.

Do not refactor this back to fixed offsets.

## The "no rank" disc (`build-placement-icon.py`)

The sign for "no rank" is a magenta disc, sitting among the medals as `Ranks/norank.png`.
`HotsRankImages.NoRank` points there, and `build-rank-assets.py` deliberately does **not**
generate this file — a shared run would overwrite it.

Nothing about its shape is guessed: segment count (16), radius ratios, and all four colours are
measured against `tools/placement-referenz.png`, a cut-out reference image taken from the game.
The script verifies the segment count against that same reference before finishing.

The disc reuses the swirl geometry from `build-free-icon.py` rather than restating the path data
a second time — see [Verifying the drawing](#verifying-the-drawing) below.

**The disc is deliberately drawn smaller than its own canvas.** Edge to edge it looked larger than
any medal even though its frame was the same size: a medal is a shield and tapers to 41 of 158
points top and bottom, a disc is full over its whole height. In the shared 71×78 box
(`Stretch="Uniform"`), `gold_3.png` renders at 70.9 × 72.7 and an edge-to-edge disc at 71 × 71 —
visibly more. The canvas is therefore **320×352**, double the medals' 160×176, with the disc drawn
at 272 inside it: rendered at **60.3**, about 15 % narrower than the medal.

Whoever changes the size compares **rendered** dimensions, not file dimensions — file size alone
says nothing about how large a `Stretch="Uniform"` image ends up on screen.

## The penalty triangle (`build-penalty-icon.py`)

`penalty.png` (128×128, RGBA) is **drawn**, not cut out. The template it is measured from shows
the icon at only about 26 px with heavy JPEG artefacts; scaled up, those artefacts read as a
defect rather than as detail. The shape is simple enough to redraw as geometry, and the colours
are measured from that same template.

Rendering happens 4× supersampled and is then downscaled, because Pillow does not antialias lines
on its own.

The result is used at two sizes: 48 px in the account dialog, where it doubles as the click
target, and 18 px in the account row, where it is a pure status indicator.

## The free-rotation mark (`build-free-icon.py`)

`free.png` (128×128, RGBA) is likewise **drawn**, not cut out — in-game the badge measures only
about 27 px, and a crop at that size looks like a defect once scaled up, the same problem as
`penalty.png`.

The shape is still not guessed. The three-armed swirl is taken as Bezier paths straight from
Blizzard's own game icon (an SVG, URL recorded in the script header) — only the three arms are
reused, since in-game they sit on a disc while the source SVG places them on a hexagon. Colours
and radii are measured from a screenshot.

The size of the swirl is **tuned, not estimated**: in the reference screenshot, 28 % of the disc
area is bright, and at `R_SWIRL = 0.57` the drawing hits 27.8 %. Whoever changes this measures it
again rather than nudging the constant by feel.

The game's bloom — the ring glows in the corner in-game — is deliberately **not** baked in: the
card the mark sits on has no fixed light source a painted highlight could match.

The script's own SVG-path parser handles only `M`, `L`, `C`, `S`, `Z`. Nothing more is needed,
because nothing else occurs in the three source templates it reads.

### Verifying the drawing

`build-placement-icon.py` imports the swirl straight from `build-free-icon.py` instead of writing
the path data a second time — it is the same swirl, and two independent copies would drift apart
at the next touch-up.

One verification metric turned out to be useless: the bright-area fraction of the ring. It
measures against the image's own mean, and the reference screenshot carries an in-game glow the
drawing does not reproduce — the value stayed at 0.38 no matter how thin the ring was drawn.

Checked instead is the **segment count**, using the same counting function on both the drawing
and the reference. That count has to average across the full width of the ring band: at a single
radius near the outer edge, the reference ring falls apart into fragments and returns 7 segments
instead of the correct 16.

## Hero portraits (`build-hero-assets.py`)

The 90 hero portraits are JPEG at 160 px, one file per hero id, and the id doubles as the file
name (`UI/Images/Heroes/{id}.jpg`) — no accents, apostrophes, or dots in an id, for exactly that
reason.

`tools/build-hero-assets.py` generates the portraits **and**
`Backend/Entity/HotsHeroCatalog.Generated.cs` in the same run. Never hand-edit the generated
catalogue file — adjust the script and re-run it; the hand-written half of the catalogue sits
beside it as a `partial` class.

The 160 px source size is not arbitrary either: it covers 64 device-independent pixels at 250 %
Windows scaling, the size the hero picker draws its circles at. An undersized source only becomes
visible on a scaled-up screen, never at 100 %.

In the picker, the circle itself comes from an `Ellipse` with an `ImageBrush`
(`Stretch="UniformToFill"`) — the roundness lives in the UI, not in the asset. That is also why
the portraits are plain square JPEG without an alpha channel: about 819 KiB for all 90 combined,
against several MB had they been PNG.

## What is NOT an asset

The four currency icons (gold, shards, gems, chests) and the archive icon are **not** PNGs. They
are XAML `Path` geometry, drawn directly in the row and dialog templates:

- a coin, a triangle, a hexagon, and a chest at 13 px for the four currencies
- lid, body, and an arrow at 17 px for the archive icon, which flips direction — inward when
  archiving, outward when restoring — so the same menu entry never shows the opposite of what it
  does

At that size, a coin or a hexagon is geometry, not image material, and colours are measured
straight from a screenshot of the in-game header bar. Four more PNG assets would each need their
own generator script, their own `Smurftown.csproj` entry, and their own `pack://` URI — the worse
trade here, unlike the penalty triangle or the free-rotation mark, whose shapes cannot be stated
in three path commands.

Full pixel budgets for both are in [`docs/ui-layout.md`](ui-layout.md).

## Adding a new image

Generate it with a script under `tools/` first — never add a PNG straight from an editor or a
screenshot crop. Then enter it in `Smurftown.csproj` as `<Resource Include>` **plus**
`<None Remove>`. Skip the entry and the `pack://` URI loads into nothing at runtime; the build
reports no error at all.
