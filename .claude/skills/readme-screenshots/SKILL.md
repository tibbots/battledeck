# Retaking the README screenshots

The images in `README.md` (and the three translations, which reference the same files) are taken
against **demo data and never against the real list**.

## Why — this is not caution

`tibbots/smurftown` is a **public** repo, and the UI shows battletag and email address in plain
text: the row shows the one, the edit dialog the other. A picture of the real list publishes 27
battletags and 27 addresses, and does so **permanently** — GitHub keeps every version of an image
in the history, including one replaced later. There is no taking it back by committing a new file.

`tools/capture-run.ps1` enforces this itself and **aborts as soon as `data.yaml` holds a single
address not ending in `@example.com`** — the `data.yaml` of the folder the app is actually running
against, which with `SMURFTOWN_HOME` set is not the one under `%USERPROFILE%`. That is the only
safeguard which does not depend on somebody remembering. Do not disable it.

## The boundary: an instance that is already running

**Claude starts Smurftown itself and closes it again — after asking.** The go-ahead is per run, not
per session; see `CLAUDE.md` → Working practice.

What changed underneath is which danger is left. `data.yaml` is still rewritten whole on every
mutation, with nothing locking it — but the capture run no longer works in the real folder at all,
so two instances writing over each other is not the risk here any more. **The drivers are.**
`drive-smurftown.ps1` and `capture-window.ps1` take the **first** Smurftown process that owns a
window: with two of them up, every shot is a coin flip, and one of the two is showing the real list.

So one instance at a time. If the one already running is the user's, ask before closing it —
`test-home.ps1` refuses to start beside it, which is the reminder, not the permission.

`tools/drive-smurftown.ps1` still starts nothing; it aborts if no instance is running. That
separation stays — the one that starts is `tools/test-home.ps1`.

## The procedure

```
1. close any running instance          the drivers take the first window they find
2. .\tools\test-home.ps1 -Fresh       demo data into %TEMP%, SMURFTOWN_HOME set, app started
3. .\tools\capture-run.ps1           checks the folder it is about to photograph, then shoots
4. Stop-Process -Id <the PID step 2 printed>
```

**Nothing is set aside and nothing is put back**, and that is the point of step 2. The old
procedure moved the real `data.yaml` out of the way and leaned on a final step to move it back —
and a final step is exactly what a run that strands halfway never reaches. Now the real folder is
not opened at all.

**Step 3 has to come after step 2** for the duller reason: the list is read once, at startup.

**`-Fresh` seeds the reserve set, not what is on the current images.** `tools/demo-data.yaml` holds
ten accounts, the images were shot against twenty-eight (table below). A faithful retake needs that
larger set in the folder first; without `-Fresh` the script keeps whatever is already there.

| Source | What it is |
|---|---|
| `tools/demo-data.yaml` | ten invented accounts, generated by `tools/gen-demo-data.py` — the **reserve** set |
| the set actually on the images | 28 demo accounts over EU and AM, with penalty games, open placements, one archived account and one complete collection |

## Driving it

`tools/capture-run.ps1` walks a human through the shots — announcement, countdown, capture.
`tools/drive-smurftown.ps1` does it without a human:

```powershell
.\tools\drive-smurftown.ps1 -Do 'front; click:139,140; wait:600; move:660,770; shot:filter-game'
```

Commands: `front`, `click:X,Y`, `right:X,Y`, `move:X,Y`, `wheel:X,Y,N`, `key:NAME`, `type:TEXT`,
`wait:MS`, `shot:NAME`.

Rules that cost time when ignored:

- **Coordinates are window-relative** — exactly what can be read off a capture. The main window is
  borderless, so its window rectangle *is* its client area: 1340×800 in the image is 1340×800 on
  the window.
- **`move:` before every `shot:`**, or a row shows up in the image in its hover state.
- **No `front` between opening a menu and clicking in it.** `SetForegroundWindow` closes any open
  popup. Bring the window forward *before* the first click of a sequence.
- **Grid positions are computed, not searched.** Where a hero sits in the picker follows from
  `HotsHeroCatalog`: groups in role order, alphabetical within, 15 per row, grid pitch 74. Illidan
  is Melee Assassin slot 2, Lúcio Healer slot 10. Searching for it in the image is guessing.
- **Capture with `CopyFromScreen`, not `PrintWindow`.** WPF popups — the start menu and a row's
  action menu — are separate windows at OS level; `PrintWindow` draws only the one asked for and
  would leave them out. On two images they are the entire point.
- **The consequence: whatever overlaps the window is in the picture.** That is what the countdown
  is for, not just for clicking. For the same reason the start menu is captured second to last: it
  closes on any click beside it, so it has to be opened last.
- **Captured is the main window's rectangle, not the active window's.** A modal then sits in front
  of the dimmed list behind it — the way it is actually used, and it shows the `DialogBounds`
  margin as a bonus. `-Foreground` switches that.

## The shot list

It lives as a data field in `tools/capture-run.ps1` — beside what executes it. What belongs here is
why the order is what it is.

| File | UI state | What it shows |
|---|---|---|
| `overview.png` | HotS + EU, no filters, archive off | the list: rank medals, hero strip, four currencies, read timestamp |
| `filter-game.png` | game filter on **Overwatch** | the game filter is a **view choice**: different rows, dashed boxes, HotS extra filters gone |
| `filter-region.png` | HotS + **AM** | region rows — 5 of them, including one with nothing but dashes |
| `hero-filter.png` | hero picker open, **Illidan + Lúcio** | role rings, role chips, hit counter |
| `hero-filter-result.png` | the list under that filter | 7 of 25 rows, button shows `ANY OF 2` |
| `rotation.png` | click on the `FREE` symbol | the 14 free heroes of the period, with nexus badges |
| `archive.png` | archive toggle on | the other half of the list |
| `actions-menu.png` | a row's action menu open | copy email, copy password, edit, archive |
| `start-menu.png` | a row's start menu open | the four modes from "Play" to "Open loot chests" |
| `edit-account.png` | dialog, ACCOUNT tab | region ticks, game ticks, battletag as display |
| `edit-hots.png` | dialog, HOTS tab | region bar (two regions), rank grid, hero grid |
| `settings.png` | SETTINGS tab | app language, game path, input speed, client language, `ABOUT & UPDATES` |
| `update-offer.png` | version chip clicked, an update pending | the chip carrying both numbers, the panel, `Install` / `What's new` |

**Why Illidan and Lúcio and not anyone**: both must be **absent** from the free rotation of the
period you are shooting in. Pick a free hero and the filter matches **every** HotS account —
`CanPlayAnyHero` lets through whoever owns it **or** can play it free — and an image where nothing
changes shows nothing. Check the running period in `Backend/Entity/rotation-calendar.yaml` and pick
two names that are not in it.

The dialog images need an account with **three** properties at once: two regions (only then does
the region bar appear in the HotS tab), penalty games, and an open placement.

## What demo data cannot show

**The reading itself cannot be captured.** It needs a real login to the game, and the demo accounts
have none. What is shown instead is the **request** (`start-menu.png`) and the **result** — the
filled row in `overview.png` with medal, hero strip, currencies and read timestamp. That these
values are read automatically out of the running game, rather than typed by hand, is what the
README says in text; an image for it would need a real account in it.

## Two shots that need a state the demo data cannot produce

**`update-offer.png` needs an update to exist**, and on a machine running the newest version none
does. Write the state file by hand before the start - the offer is shown from that file, on the
first frame, without asking the network:

```yaml
# %TEMP%\smurftown-test-home\update.yaml
lastCheck: 2026-08-22T18:53:00.0000000+00:00
latestVersion: 1.0.1
```

Keep `lastCheck` recent, or the start asks GitHub and overwrites the invented version with the
truth. **The chip is only clickable while something is offered** - `IsHitTestVisible` hangs on
`UpdateOffer.CanOpen`, so in the quiet state it is a badge and the click does nothing.

**`settings.png` shows the path this build runs from**, in the *Self-update* row. Out of
`bin/Debug` that row reads `not possible - development build` and carries a path with somebody's
user name in it - neither is what a reader installs. So capture from a published build, in a
folder whose path names nobody:

```powershell
.\dev.cmd publish
Copy-Item dist\publish\* C:\Users\Public\Smurftown\ -Recurse -Force
.\tools\test-home.ps1 -Exe 'C:\Users\Public\Smurftown\Smurftown.exe'
```
