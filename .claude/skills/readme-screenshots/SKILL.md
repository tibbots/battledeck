# Retaking the README screenshots

The images in `README.md` and its three translations are taken against **demo data and never
against the real list** — and each of the four READMEs now shows the app in **its own language**,
not one shared English set.

## Why — this is not caution

`tibbots/battledeck` is a **public** repo, and the UI shows battletag and email address in plain
text: the row shows the one, the edit dialog the other. A picture of the real list publishes those
values permanently — GitHub keeps every version of an image in the history, including one replaced
later. There is no taking it back by committing a new file.

`tools/capture-run.ps1` enforces this itself and **aborts as soon as `data.yaml` holds a single
address not ending in `@example.com`** — the `data.yaml` of the folder the app is actually running
against, which with `SMURFTOWN_HOME` set is not the one under `%USERPROFILE%`. That is the only
safeguard which does not depend on somebody remembering. Do not disable it.

## The boundary: an instance that is already running

**Claude starts Battledeck itself and closes it again — after asking.** The go-ahead is per run, not
per session; see `CLAUDE.md` → Working practice.

What changed underneath is which danger is left. `data.yaml` is still rewritten whole on every
mutation, and the lock around that covers one process and not two — but the capture run no longer
works in the real folder at all, so two instances writing over each other is not the risk here any
more. **The drivers are.**
`drive-battledeck.ps1` and `capture-window.ps1` take the **first** Battledeck process that owns a
window: with two of them up, every shot is a coin flip, and one of the two is showing the real list.

So one instance at a time. If the one already running is the user's, ask before closing it —
`test-home.ps1` refuses to start beside it, which is the reminder, not the permission.

`tools/drive-battledeck.ps1` still starts nothing; it aborts if no instance is running. That
separation stays — the one that starts is `tools/test-home.ps1`.

## One language at a time, four passes

Layout is language-independent — pixel positions come from fixed budgets (`docs/ui-layout.md`),
not text length, so the **same click coordinates work in all four languages** — with one exception:
the hero picker's **`clear all`** button is sized to its own translated label, not to a budget, so
its position moves with the language exactly like the hero-filter chip does. That single click is
called out below, where the sequence uses it. Otherwise what changes between passes is only:
`app.yaml` → `settings.appLanguage`, and the `-Lang` flag on the capture tools that routes shots
into their own subfolder.

```
1. close any running instance
2. .\tools\test-home.ps1 -Fresh -NoStart          demo data into %TEMP%, nothing started yet
3. write app.yaml by hand with the target appLanguage BEFORE the first start (see below) -
   otherwise the app picks the system UI language on first launch
4. start the published exe (see "settings.png" below for why it must be published, not Debug)
5. run the shot sequence with drive-battledeck.ps1 -Lang <de|fr|es> (omit -Lang for English)
6. Stop-Process, then repeat from 2 for the next language
```

`app.yaml` (written directly into `%TEMP%\battledeck-test-home\app.yaml`, before the first start):

```yaml
schemaVersion: 1
appVersion: 1.6.0
settings:
  hotsPath: ''
  inputSpeed: Normal
  clientLanguage: German
  appLanguage: German   # English | German | French | Spanish
```

**Nothing is set aside and nothing is put back**, and that is the point of step 2. The old
procedure moved the real `data.yaml` out of the way and leaned on a final step to move it back —
and a final step is exactly what a run that strands halfway never reaches. Now the real folder is
not opened at all.

**`-Fresh` seeds exactly what the shot list needs.** `tools/demo-data.yaml` (generated by
`tools/gen-demo-data.py`) holds **thirteen** accounts, and every account the shot list names by
battletag — `MARBLEFOX`, `HALFMOONBAY`, `GLASSFERN` — is really in there. That was not always true:
until 24.08.2026 the script referenced a richer, never-committed 28-account set while the checked-in
`demo-data.yaml` held only ten generic ones, so a faithful retake was quietly impossible. The gap is
closed — what `-Fresh` seeds is what every shot below is measured against.

| Account | Trait |
|---|---|
| `SMURFKING` | two regions on one account |
| `NEXUSNOMAD` | open placement matches |
| `GHOSTLANE`, `SILENTPUSH` | leaver-penalty status |
| *(no name)* | never read: no battletag, email as row name |
| `ARAMANDA` | Asia — the third region abbreviation |
| `RETIREDALT`, `GLASSFERN` | archived |
| `LANEBULLY` | the highest rank on the list |
| `TOWERDIVE` | Americas ticked, never read there |
| `PAYLOADONLY` | no HotS checkbox — invisible under the HotS filter |
| `MARBLEFOX` | two regions **and** penalty games **and** an open placement, together — what the account dialog shots need |
| `HALFMOONBAY` | Americas ticked, never read — the AM filter's own dashed row |

## Driving it

`tools/capture-run.ps1` walks a **human** through the shots — announcement, countdown, capture; it
does not click anything itself. `tools/drive-battledeck.ps1` does the clicking too:

```powershell
.\tools\drive-battledeck.ps1 -Do 'front; click:139,140; wait:600; move:660,770; shot:filter-game'
.\tools\drive-battledeck.ps1 -Lang de -Do 'front; move:20,780; shot:overview'
```

Commands: `front`, `click:X,Y`, `right:X,Y`, `move:X,Y`, `wheel:X,Y,N`, `key:NAME`, `type:TEXT`,
`wait:MS`, `shot:NAME`. `-Lang de|fr|es` routes every `shot:` in that call to
`docs/images/<lang>/<name>.png`; omit it for English (`docs/images/<name>.png`).

The full sequence for the twelve non-`update-offer` shots, unchanged across all four languages
except the one `click:<clear-all-x>,52` marked below — substitute the language's own value from the
table further down before running it:

```
front; move:20,780; shot:overview;
click:139,139; wait:400; move:20,780; shot:filter-game;
click:207,139; wait:300; click:450,139; wait:400; move:20,780; shot:filter-region;
click:409,139; wait:300; click:104,202; wait:400; click:193,478; wait:200;
wheel:600,400,-4; wait:300; click:785,577; wait:300; wheel:600,400,10; wait:300;
move:1250,650; shot:hero-filter;
key:escape; wait:400; move:20,780; shot:hero-filter-result;
click:100,202; wait:400; click:<clear-all-x>,52; wait:300; key:escape; wait:300;
click:588,139; wait:400; move:20,780; shot:rotation;
key:escape; wait:300; click:980,139; wait:400; move:20,780; shot:archive;
click:980,139; wait:400; click:1291,291; wait:400; shot:actions-menu;
key:escape; wait:300; click:1249,291; wait:400; shot:start-menu;
key:escape; wait:300; click:100,485; wait:500; shot:edit-account;
click:321,112; wait:400; move:1200,20; shot:edit-hots;
click:381,736; wait:400; click:270,66; wait:400; move:20,780; shot:settings
```

Rules that cost time when ignored:

- **Coordinates are window-relative** — exactly what can be read off a capture. The main window is
  borderless, so its window rectangle *is* its client area: 1340×800 in the image is 1340×800 on
  the window.
- **`move:` before every `shot:`**, or a row shows up in the image in its hover state.
- **No `front` between opening a menu and clicking in it.** `SetForegroundWindow` closes any open
  popup. Bring the window forward *before* the first click of a sequence.
- **The app must be on the ACCOUNTS tab before this sequence starts.** A prior run that ended on
  SETTINGS leaves every click in this sequence landing on the wrong screen — and nothing reports
  it, every `shot:` just quietly captures the same Settings frame. Measured: an entire redo of a
  language pass, caught only because every file came out the same byte size.
- **The SETTINGS tab click is `270,66`, not `347,66`.** `ACCOUNTS` and `SETTINGS` are each a
  fixed-width 160 px button (`docs/ui-layout.md`, "Main window tabs"), but the visible label sits
  well short of that box's own right edge — `347` cleared the word and landed in the button's own
  blank margin, and a click that lands on nothing reports nothing: no error, no different frame, the
  view simply stays wherever it already was. `270` sits on the label itself and is verified against
  all four languages in this pass, since the tab bar — unlike the hero picker below — is governed by
  the fixed layout budget and not by translated text width.
- **Clear the hero filter through the picker, not through the chip's `×`.** The chip's own width
  depends on the translated label (`ANY OF 2` in English, `EINER VON 2` in German — visibly wider),
  so a fixed pixel for the `×` that works in English lands on the chip's middle in German and
  reopens the picker instead of clearing it — while everything downstream (rotation, archive,
  actions-menu, start-menu, the account dialog) silently keeps filtering on the two picked heroes.
  The sequence above avoids the chip for exactly this reason: it reopens the picker (`click:100,202`,
  safe — well inside the chip regardless of label width) and clicks **`clear all`** inside the modal
  before closing with `Escape`.

  **That inner button carries the same disease, one level down — an earlier version of this
  document claimed the opposite.** "Fixed position, independent of outer state" was wrong: the pill
  is sized to its own translated text exactly like the chip it exists to be safer than, so its centre
  moves with the label just the same. Measured against the running app, one hero-picker header at a
  time:

  | Language | Label | `clear-all-x` |
  |---|---|---|
  | English | "clear all" | 556 |
  | German | "alle abwählen" | 642 |
  | French | "tout effacer" | 638 |
  | Spanish | "borrar todo" | 638 |

  **Measured wrong once already**: clicking German's `642` while the app spoke English landed on
  `select all` instead, which ticks all 90 heroes rather than none — the hero filter then matches
  every account instead of two, and every shot after it is silently wrong in a way that looks
  identical to a correct one until read closely.

  **How to re-measure it** — for a language not in the table, or after the header changes again:
  open the hero picker, take a check-shot, and read the button's own left and right border off the
  image rather than eyeballing the label. Its centre is `clear-all-x`. Click it, take a second
  check-shot, and confirm the counter actually reads **zero selected** (whatever that string is in
  the language at hand) before trusting the value and moving on to the shots that depend on it.
- **Grid positions are computed, not searched.** Where a hero sits in the picker follows from
  `HotsHeroCatalog`: groups in role order, alphabetical within. Illidan is Melee Assassin slot 2,
  Lúcio Healer slot 10 — both fixed regardless of the picker's scroll position or the app's
  language. Searching for it in the image is guessing.
- **Capture with `CopyFromScreen`, not `PrintWindow`.** WPF popups — the start menu and a row's
  action menu — are separate windows at OS level; `PrintWindow` draws only the one asked for and
  would leave them out. On two images they are the entire point.
- **The consequence: whatever overlaps the window is in the picture.** That is what the countdown
  is for, not just for clicking.
- **Captured is the main window's rectangle, not the active window's.** A modal then sits in front
  of the dimmed list behind it — the way it is actually used, and it shows the `DialogBounds`
  margin as a bonus. `-Foreground` switches that.

## The shot list

It lives as a data field in `tools/capture-run.ps1` — beside what executes it. What belongs here is
why the order is what it is, and what each shot actually shows against the current demo data.

| File | UI state | What it shows |
|---|---|---|
| `overview.png` | HotS + EU, no filters, archive off | the list: rank medals, hero strip, four currencies, read timestamp — 8 of 8 rows |
| `filter-game.png` | game filter on **Overwatch** | the game filter is a **view choice**: different rows, dashed boxes, HotS extra filters gone |
| `filter-region.png` | HotS + **AM** | region rows — 4 of them (`SMURFKING`, `MARBLEFOX`, `SMURFKING`, `TOWERDIVE`), `HALFMOONBAY` with nothing but dashes |
| `hero-filter.png` | hero picker open, **Illidan + Lúcio** | role rings, role chips, hit counter — 2 selected, 5 entries match |
| `hero-filter-result.png` | the list under that filter | 4 of 8 rows, button shows `ANY OF 2` |
| `rotation.png` | click on the `FREE` symbol | the free heroes of the period, with role rings on each |
| `archive.png` | archive toggle on | the other half of the list — `GLASSFERN` and `RETIREDALT`, 2 of 2 |
| `actions-menu.png` | a row's action menu open | copy email, copy password, edit account, archive |
| `start-menu.png` | a row's start menu open | the four modes from "Play" to "Open loot chests" |
| `edit-account.png` | dialog, ACCOUNT tab, opened from `MARBLEFOX`'s row | region ticks, game ticks, battletag as display |
| `edit-hots.png` | dialog, HOTS tab | region bar (two regions), penalty triangle, placement checkbox, rank grid — all three at once, see below |
| `settings.png` | SETTINGS tab | app language, game path, input speed, client language, `ABOUT & UPDATES` |
| `update-offer.png` | version chip clicked, an update pending | the chip carrying both numbers, the panel, `Install` / `What's new` — its own short run, see below |

**Why Illidan and Lúcio and not anyone**: both must be **absent** from the free rotation of the
period you are shooting in. Pick a free hero and the filter matches **every** HotS account —
`CanPlayAnyHero` lets through whoever owns it **or** can play it free — and an image where nothing
changes shows nothing. Check the running period in `Backend/Entity/rotation-calendar.yaml` and pick
two names that are not in it. As of this writing neither is, on any period checked.

**The dialog images need an account with three properties at once**: two regions (only then does
the region bar appear in the HotS tab), penalty games, and an open placement — `MARBLEFOX` carries
all three on its Europe region. Opening the dialog from a different row (or a stale filtered list
that reorders which row is third) captures the wrong account; see the "must be on ACCOUNTS tab
first" and "clear the hero filter properly" traps above — both were measured causes of exactly
this failure.

## What demo data cannot show

**The reading itself cannot be captured.** It needs a real login to the game, and the demo accounts
have none. What is shown instead is the **request** (`start-menu.png`) and the **result** — the
filled row in `overview.png` with medal, hero strip, currencies and read timestamp. That these
values are read automatically out of the running game, rather than typed by hand, is what the
README says in text; an image for it would need a real account in it.

## Two shots that need a state the demo data cannot produce

**`update-offer.png` needs an update to exist**, and on a machine running the newest version none
does. It also needs the header chip to show the offer on **every other shot's opposite** — the
quiet `v1.6.0` badge — so it is captured in its **own short-lived instance**, separate from the
twelve-shot sequence above, not folded into it.

```powershell
# stop the running instance first, then, before starting it again:
# %TEMP%\battledeck-test-home\app.yaml, in the update: section
```

```yaml
update:
  lastCheck: 2026-08-24T14:20:00.0000000+00:00   # a few minutes in the PAST of real now, not the future
  latestVersion: 1.6.1
```

Then start, and immediately: `front; wait:200; click:1287,64; wait:400; move:20,780; shot:update-offer`.

**`lastCheck` in the future breaks this silently.** A timestamp ahead of real time does not read as
"very recent" — measured: the app treated it as needing a check anyway, queried GitHub for real,
and overwrote the seeded `1.6.1` with the actual latest release before the chip was even clicked.
The capture then shows the quiet state with nothing to click. Use a `lastCheck` a few minutes
**before** actual now, not after.

**`settings.png` shows the path this build runs from**, in the *Self-update* row. Out of
`bin/Debug` that row reads `not possible - development build` and carries a path with somebody's
user name in it — neither is what a reader installs. So capture from a published build, in a
folder whose path names nobody, and reuse that same publish for every language pass and for
`update-offer.png`:

```powershell
.\dev.cmd publish
Copy-Item dist\publish\* C:\Users\Public\Battledeck\ -Recurse -Force
# then start it with $env:SMURFTOWN_HOME pointed at the test-home folder, e.g.:
$env:SMURFTOWN_HOME = "$env:TEMP\battledeck-test-home"
Start-Process 'C:\Users\Public\Battledeck\Battledeck.exe'
```
